# 持续集成

> 🌐 本文档由 [denoland/deno](https://github.com/denoland/deno) 翻译,英文原版见原项目。

本页说明主 CI 工作流的结构、它如何决定运行哪些任务,以及"仅文档"快速通道。

## 工作流是生成的,不是手写的

CI 工作流是**生成**出来的。唯一事实来源是 `.github/workflows/ci.ts`——一个 Deno 脚本,它构建工作流对象并写入 `.github/workflows/ci.generated.yml`。永远不要直接改 `.yml`;它带着 `GENERATED BY ./ci.ts -- DO NOT DIRECTLY EDIT` 头部。

修改 `ci.ts` 后重新生成:

```bash
deno run -A .github/workflows/ci.ts
```

`.github/workflows/` 里的其他工作流都遵循同样的 `*.ts` → `*.generated.yml` 模式。

## 任务总览

在 pull request 上,工作流大致运行:

- **`pre-build`** — 快速门禁任务。它决定下游任务是否应该运行,并通过任务输出暴露这个决定。
- **`build`**(按平台)与 **`build libs`** — 编译 Deno 和 `deno_core` 库。
- **`test`**(按平台,分片)— spec、unit、node-compat 和 WPT 套件,依赖 `build`。
- **`bench`** — 基准测试。
- **`deno-core-test`** 与 **`deno-core-miri`** — `deno_core` / `libs/*` crate 测试(后者在 Miri 下运行)。
- **`lint`** — 格式化检查、jsdoc 检查,以及 `tools/lint.js`(Rust + JS)。
- **`ci-status`** — 汇聚任务,分支保护规则以它为准。只要它的依赖没有一个失败或被取消就通过;被跳过的依赖不算。

## `pre-build` 如何门禁其余部分

`pre-build` 运行几个轻量检查,把结果发布为输出,供下游任务在 `if:` 条件中读取:

- `skip_build` — 当草稿 PR 未选择加入 CI 时设置。为 true 时,build、test、lint、bench 和 `deno_core` 任务全部跳过。
- `skip_deno_core_test` — 当没有 `deno_core` 相关文件变更时设置,`deno_core` crate 测试可以跳过(`tools/check_deno_core_changes.js`)。
- `docs_only` — 当 PR 只动了 `doc/` 目录时设置(`tools/check_docs_only_changes.js`)。

每个被门禁的任务的 `if:` 组合相关输出,例如:

```
needs.pre_build.outputs.skip_build != 'true' &&
  needs.pre_build.outputs.docs_only != 'true'
```

## 仅文档快速通道

只改 `doc/` 下文件的 pull request 不需要编译或测试任何东西。对这类 PR,CI 只跑 `lint` 任务,跳过其他一切。

工作原理:

1. 在 `pre-build` 中,`tools/check_docs_only_changes.js` 将 PR 与其基线 SHA 做 diff。如果所有变更文件都在 `doc/` 下(且至少有一个文件变更),它把 `docs_only=true` 写入任务输出。diff 为空或失败时默认 `false`,拿不准就走完整流水线。
2. build、build-libs、test、bench、`deno-core-test` 和 `deno-core-miri` 任务各自在运行条件中追加 `&& docs_only != 'true'`,所以在仅文档 PR 上它们被跳过。`test` 任务依赖 `build`,跳过 `build` 会自动级联到它们。
3. `lint` 任务刻意**不**受 `docs_only` 门禁。它照常运行,也就是说 Markdown 仍然会被格式化检查和 lint(`deno fmt --check` 覆盖 `doc/`)。这就是"只 lint、其他什么都不跑"的行为。
4. `ci-status` 照常运行并通过:它被跳过的依赖既不算失败也不算取消,而 `lint` 是成功的,于是必需的状态检查变绿,PR 可以合并。

一旦 PR 动了 `doc/` 之外的任何东西,`docs_only` 就是 `false`,完整流水线照常运行。

## 修改 CI 行为

要改变运行哪些任务或增加新门禁:编辑 `ci.ts`,重新生成 YAML,两者一起提交。生成文件会入库,这样审查者能在 diff 中看到生效的工作流。
